# Decisions

Settled in a grill-me session before any code was written (Jeff decides; Athena, the coding agent, researched the facts and proposed defaults). Later redirects are logged at the bottom along with who raised them.

## Scope
1. **Goal:** onboard a CARIN Blue Button payer through configuration, not code. Given a FHIR base URL, produce a working config, recorded fixtures, normalized claims, and a data-quality score.
2. **Language:** TypeScript on Node 24 (native type stripping), with one runtime dependency (`yaml`).
3. **MVP:** discover, probe and record, normalize and dedupe, scorecard.
4. **No LLM at runtime.** Agents helped build it, but onboarding itself is deterministic, reproducible and auditable, which matters for health data.

## Config
5. **Three layers, merged leaf by leaf:** spec (what the IG requires), then vendor (what a server product does), then payer (one endpoint), then hand-written `overrides`. `explain` shows which layer set each value.
6. **The spec layer is generated** from the CARIN IG's own published CapabilityStatement (v2.2.0), not retyped by hand.
7. **Discovery records claims; probing tests behavior.** CapabilityStatements are self-reported, so every claim is checked against what the server actually returns.

## Data
8. **Sources:** CMS Blue Button 2.0, plus the public HAPI and Firely test servers. CMS was planned to run from its published synthetic sample. It now runs live through SMART on FHIR OAuth as a synthetic member, and the sample remains as an offline fallback (*updated during the build*). Both public servers accept writes from anyone, so we score **recorded fixtures**, not live reads.
9. **Synthetic data only, as far as can be checked.** Every source is a sandbox or public test server. Public test servers accept writes from anyone, so nothing can prove every record is fake; that is why the scrub exists and fails closed (R7, R10, R16).
10. **Canonical model:** Claim and Member, stored in SQLite (`node:sqlite`, no install). Coverage is recorded but not yet normalized (*updated during the build*).
11. **Dedupe:** (a) the same claim repeated within one source, keyed on payer plus CARIN unique claim ID, with a fingerprint fallback that never merges two claims the payer gave different IDs (see R13); (b) the same claim from two sources. A constructed fixture was planned because no two of the three servers share a patient identifier. It turned out to be unnecessary: Firely holds a real two-source scenario (20 people in `ehr-a` and `ehr-b`, linked by a master patient index id), so no data is constructed (*updated during the build*).
12. **Member matching is deterministic only** (shared identifiers). Probabilistic matching on names and dates of birth is future work and needs human-review thresholds.
13. **Scores before and after normalization.** Normalization may only fix what is genuinely fixable (duplicates, code-system labels, formats), never invent missing data. Each point gained is attributed to the rule that earned it, and the raw and normalized scores are observed independently of the fix log (see R12).
14. **The scorecard is PIQI-inspired, not a PIQI implementation.**

## Findings
- None of the three servers declares a CARIN profile in its CapabilityStatement, not even CMS, whose actual data is CARIN-profiled. That is the reason for decision 7.

## Redirects log
_Each entry: what the agent proposed, what changed, who raised it, and why._

**R1, `_id` search counted as a hard failure (slice 1 review).** The agent counted CMS's missing `_id` search as a SHALL failure. CMS supports `read`, and `GET ExplanationOfBenefit/123` serves the same use case, so that scoring made CMS look worse than it is. *Change:* the gap is still reported, marked "equivalent available," and left out of the failure count. *Raised by:* Athena at the checkpoint; *decided by:* Jeff.

**R2, rediscovery silently dropped hand edits (slice 1 review).** `discover` rewrote `payers/<id>.yaml` from scratch, so a payer's real rate limit added under `overrides:` would disappear on the next run, and payer endpoints change. *Change:* rediscovery keeps `overrides:` and prints any drift (new or closed gaps, software or auth changes). A test covers it. *Raised by:* Athena while self-reviewing; *decided by:* Jeff.

**R3, a guessed default presented as fact (slice 1 review).** The spec layer's default of 2 requests per second is a guess, because no payer publishes a rate limit in its CapabilityStatement. *Change:* it is labeled under `assumptions:`; probing counts 429 responses and suggests a per-payer override. *Raised by:* Athena; *decided by:* Jeff.

**R4, the search check reported a false "honored" (slice 2 verification).** The first version of the search check only tested a positive filter: did every returned claim match? Firely passed four parameters it doesn't support. Manual verification showed Firely **silently ignores** unsupported parameters: `type=zzz-nonexistent` returns all 1,590 claims, the parameter is dropped from the Bundle's self link, and only a warning is buried in the response. Its unfiltered first page happened to match the filters. *Change:* every check now also runs a **negative control**, a value that cannot match, and a server that returns claims for it is marked `ignored`. Unit tests use a fake ignoring server. *Raised by:* Athena's own verification of a suspicious result.

**R5, "rejected" reported where the payer only wanted a different form (CMS live probe).** Three CMS checks failed on our query format, not on the server: `patient=Patient/<id>` returns 403 but the bare id works; `type` needs CMS's own codes (`pde`, `carrier`); `service-date` needs a `ge`/`le` prefix. *Change:* each check tries the spec form first, then common variants, reports which one works, and *suggests* it as config (`searchVariants`). A human applies suggestions with `accept <payer>`; they are never applied automatically. *Raised by:* Athena verifying the first live CMS run; *decided by:* Jeff.

**R6, full-sync rule narrowed (slice 2 follow-up).** Jeff's first call was to mark Firely full-sync-only because it ignores filters. The agent's framing ("a date filter would re-download everything") was imprecise: incremental sync depends on `_lastUpdated`, which all three payers honor. *Change:* a broken `_lastUpdated` means full sync; any other ignored filter means client-side filtering. *Decided by:* Jeff, after the agent corrected its own framing.

**R7, publishing recordings (slice 2).** Public test servers accept writes from anyone. *Change:* recordings are committed for reproducibility, but any patient without a synthetic marker (HTEST tag, negative CMS id, `-SYN-` id, "Synthetic" or Synthea-style name) has its name, address, telecom and full birth date removed and its identifiers hashed, so cross-source matching still works. *Decided by:* Jeff.

**R8, fingerprint dedupe merged different claims (slice 3 verification).** The first fingerprint (person + date + NPI + codes + amount) flagged 29 Firely duplicates. Checking every pair showed 9 false positives: same patient and date but different diagnoses, claim types or providers. Those claims had no procedure codes and a placeholder "NPI" (`Prac-00001`). *Change:* NPIs are validated with the CMS check digit; a fingerprint now requires a valid NPI **and** at least one procedure code, and includes claim type. Result: 18 duplicates, every one a true cross-source pair (`ehr-a` / `ehr-b`, linked by a shared MPI id). The two pairs it now misses carry check-digit-failing NPIs and a $9,999 sentinel amount: planted defects in the test data. A missed duplicate is preferred to a false merge. *Raised by:* Athena's pair-by-pair verification.

**R9, a human-review tier for near-duplicates (slice 3 review).** Strict dedupe leaves pairs that match on everything except a valid NPI. *Options weighed:* leave them, loosen the rule, or queue them. *Change:* such pairs go to a `review` table with the reasons they were not merged (check-digit failure, sentinel amount, different source records) and an empty `decision` column for a person. High-confidence matches merge automatically; the middle band goes to a human; nothing is merged silently. On the test data the queue holds exactly the two planted-defect pairs. *Decided by:* Jeff.


## Independent review (Fable 5.2, a second model)
After the first publish, Jeff had the repo reviewed by a different model (Claude Fable 5.2) with a skeptical brief: correctness, FHIR/CARIN domain, privacy, data-engineering design, test gaps and overstated claims. It scored the repo 7/10 and raised three blockers. Athena checked each finding it acted on against the code and the committed data; Jeff approved the fix plan. Findings not acted on are listed at the end with their status.

**R10, the scrub covered only Patient (review F1, blocker).** Scrubbed patients' Coverage still carried a member id (`TEST-SUB-001`) and their Patient records kept race and ethnicity extensions; the values were test data, but "scrubbed" overstated what the code did. *Change:* Patient is reduced to an allowlist (anything not named is dropped), and the same member's Coverage and claims lose names, free text, contained resources and member ids, which are hashed. A test plants nine kinds of identifying data and asserts none survives. *Raised by:* Fable 5.2; *verified by:* Athena; *decided by:* Jeff.

**R11, an erroring negative control counted as "returned 0" (review F2, blocker).** R4's fix had its own blind spot: a negative control that came back 400 or 403 was read as "no claims", so CMS's `patient` and `type` verdicts rested on errors. *Change:* an erroring control proves nothing. The probe falls back to the server's `Bundle.total` against an unfiltered baseline, and otherwise reports `unverified`. Re-probing CMS: `type` is honored on real evidence (total 155 → 1); `patient` is now `unverified`, because a token that sees one member can't distinguish filtering from no filtering. A 401 now stops the probe instead of being recorded as `rejected`. *Raised by:* Fable 5.2; *decided by:* Jeff.

**R12, the raw score was derived from the normalizer's own fix log (review F3, blocker).** "Raw fails" meant "a fix rule fired", so a fix that silently did nothing, or a rule that changed data without logging, could not be detected, and the attribution check was arithmetic over the same source. *Change:* two independent observers (`observe.ts`) read the FHIR as sent and the normalized row; neither reads the fix log. Reconciliation requires every fail-to-pass change to be explained by a logged rule allowed to cause it, and fails on regressions. Mutation tests plant one defect at a time through the real normalizer. *What it found on first run:* 314 Firely and HAPI claims improved with no rule credited, because restoring a missing adjudication system also makes the billed amount readable. The old scorer had overstated their raw scores by about 3 points (Firely 83.6 → 80.3, HAPI 87.5 → 84.5). *Raised by:* Fable 5.2; *decided by:* Jeff.

**R13, the fingerprint was not a fallback (review F6).** Two claims from one payer with different CARIN claim ids, such as a repeat visit on the same day, could still be fingerprint-merged. The new mutation tests hit this immediately. *Change:* the fingerprint never merges claims a payer gave different ids; it still matches the same claim across sources. No change on the test data (all 18 duplicates are cross-source). *Raised by:* Fable 5.2, confirmed by a failing test.

**R14, survivorship ignored sensitivity labels (review F14).** Firely's twins differ in labels: `ehr-a-p100` is Restricted and tagged as Part 2 origin, its twin is Normal, and the survivor was chosen by sort order. *Change:* the survivor keeps the most restrictive confidentiality code and every other sensitivity tag of its duplicates. The agent's first version took a union of codes and produced "N" plus "R" on one claim; inspecting the output showed confidentiality is a single ranked scale, and it was corrected. On this data every restricted claim already survives, so the rule changes nothing here; a test covers the reverse case. *Raised by:* Fable 5.2; *corrected by:* Athena's output check.

**R15, smaller fixes from the same review.** Versioned references (`Patient/1/_history/2`) resolve to the resource; a resource repeated across pages is recorded once; a clone path with spaces works; the bearer token is sent only to the payer's own origin, and client credentials only to an https token endpoint; a changed auth endpoint on rediscovery is flagged for review; service-date checks also read `item.servicedDate`/`servicedPeriod`; a page that fails mid-collection is recorded as partial. Tests cover the reference, credential-origin and 401 cases; the rest are small guards without dedicated tests yet.

**Not changed, with reasons.** The review noted that a bare patient id and an ICD code listed under both `icd-10-cm` and `icd-10` are legal FHIR. Agreed. The bare id is handled as a query variant and isn't scored. The double-listed code is still scored under Conformity, as a deliberate consistency choice (one code, one canonical system, so downstream counts don't double); the README says so, because it is most of CMS's +4.4. The same applies to day-precision dates. CMS's `identifier` search stays reported as ignored, which is what it does.

### Round 2
Fable 5.2 re-reviewed the fixes: 8/10, with the observers, the `unverified` verdict and this log called out as the strongest parts. It found that several round-1 fixes were incomplete, and that some of the new text overclaimed.

**R16, the scrub failed open (round 2 N1, N3).** Only patients in the recording were judged, and the recording stops at 50 patients. Re-recording showed **101 HAPI claims and 150 Firely claims** whose member was never fetched had been published unscrubbed. The R10 version also deleted contained resources, which is where some claims keep the provider NPI. *Change:* a claim or Coverage stays as sent only if its member is a recorded patient with a synthetic marker; everything else is scrubbed. Reference display names are stripped everywhere, along with addresses, accident details and extensions. Contained Patient, RelatedPerson and Person resources are dropped; contained providers stay. Tests cover an unfetched member, a contained patient, an identifier-only reference and a contained provider. Scores and dedupe are unchanged. *Raised by:* Fable 5.2; *confirmed by:* the re-recording.

**R17, R13's guard depended on order (round 2 N4).** It compared only against the first claim holding a fingerprint. Payer a's claim plus payer b's two same-day claims with different ids made b's repeat visit disappear. *Change:* fingerprint groups are decided whole. If any payer in a group issued two different claim ids for it, nothing in the group merges on the fingerprint. *Source versus payer:* Firely's `ehr-a` and `ehr-b` records come from one server, so the code treats them as one payer. None of the 18 merged pairs carries a claim id on either side; they merge only through the fallback, which is its purpose. If two sources both issued ids, they would not merge, and a production version would key on the source system, not the server. *Raised by:* Fable 5.2.

**R18, `unverified` was ignored downstream (round 2 N5).** A fresh CMS onboarding no longer suggested `patient: bare-id`, though the spec form returns 403. *Change:* an alternative form that the server accepts is suggested even when its filtering is unverified, with a note to re-test with a token that sees more than one member. "Nonstandard form" is now "alternative form" (round 1 F17).

**R19, the raw observer compared dates as strings (round 2 N7, N10).** `start: "2025-01-02T10:00:00Z", end: "2025-01-02"` failed `period-order` raw and passed normalized, so reconciliation would fail on legal data. *Change:* plausibility compares calendar days, and the raw observer ignores non-numeric amounts as the normalizer does.

**R20, overclaims corrected (round 2 N8, N11, N15, F27).** "Two independent observers evaluate every check" is now "15 field-level checks, independently of the fix log", with the shared definitions and the dedupe-based uniqueness check disclosed. The one inferring rule, `adjudication-system-restored`, is disclosed beside the scores, because it is most of the Firely and HAPI gains. Decision 9 no longer claims what can't be proven. The searches tested exclude `_id`, and the README says so.

### Open, not done
From the two review rounds, known and not fixed in this version:
- Provider matching by reference rather than NPI (F13), and `identifier.system`, modifiers and units in dedupe keys.
- Survivor choice is the lowest key, so a cancelled copy can survive over an active one (F14 remainder). Labels are inherited correctly.
- The `Bundle.total` fallback uses one cached baseline and can be fooled by writes in between on a public server (N6). A stronger control would compare two valid values for disjoint results.
- Explanation is per claim and rule, not per field (N9); `relativeRef` rejects ids with underscores (N12), though such claims are now scrubbed rather than leaked; search checks reuse the first refreshed token (N13).
- No dedicated tests yet for `item.serviced`, duplicate ids in paging, `accept`, the auth callback, or a golden scorecard; the remaining round-1 nits (F11, F15, F16, F19, F21, F23–F25).
